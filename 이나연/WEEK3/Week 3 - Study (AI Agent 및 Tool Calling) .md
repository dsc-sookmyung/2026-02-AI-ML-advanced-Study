## AI에이전트

## Part 1. AI 에이전트란 무엇인가

### 핵심 아이디어

> **LLM에게 도구를 쥐여 주고, 답이 나올 때까지 스스로 판단하면서 도구를 쓰게 하자.**
> (사람이 시키지 않아도 LLM이 알아서 흐름을 짜도록 하기)

AI Agent는 챗봇, RAG와 구조가 본질적으로 다릅니다. LLM이 답을 한 번에 만드는 것이 아니라, 여러 도구를 고르고 순서까지 직접 정해서 답이 나올 때까지 반복합니다.


챗봇, RAG, Agent는 포함 관계가 아니라 **독립적으로 함께 활용하는 것**으로 이해합니다.

### Agent = LLM + 도구 + 반복

| 구성 요소 | 역할 | 핵심 포인트 |
|---|---|---|
| **LLM** | 사고와 판단의 두뇌 | 에이전트의 결정 엔진. 자연어 요청을 받아 다음 행동을 결정. 성능과 비용 사이의 trade-off 고려 필요 |
| **도구 (Tool)** | LLM이 외부 세계에 닿는 통로 | LLM이 호출할 수 있는 함수 (Python 함수 형태). 에이전트의 능력은 어떤 도구를 쥐여주느냐에 따라 대부분 결정됨 |
| **반복 (Loop)** | 답이 나올 때까지 흐름을 반복 | LLM 응답 하나가 최종 답이 아니라 다음 단계의 지시일 수 있음. 도구 결과를 다시 LLM에 넘겨 사고하게 하며 사이클 반복 |

- LLM은 도구를 **직접 실행하지 않습니다.** 신호를 JSON 텍스트로 보내면 외부 시스템이 실제 함수를 호출합니다.
- 세 가지가 **모두** 있어야 에이전트입니다.
  - LLM만 있으면 → 챗봇
  - 검색이 1회이면 → RAG
- 에이전트는 자동 로봇이 아니라 **LLM이 도구 호출을 결정하는 구조**일 뿐입니다. 도구가 없으면 아무것도 못 하므로, 좋은 도구를 잘 설계해야 합니다.

### ReAct 패턴

**Reasoning(추론) + Acting(행동)** 을 형식화한 패턴으로, 대부분의 에이전트 프레임워크의 기본 뼈대입니다.

1. **Thought (사고)**: LLM이 현재 상황을 정리하고 다음에 할 일을 계획
2. **Action (행동)**: 어떤 도구를 어떤 인자로 호출할지 결정하여 신호를 보냄
3. **Observation (관찰)**: 도구가 돌려준 결과를 받아 정보로 흡수
4. **Answer (답)**: 충분한 정보가 모였다고 판단되면 최종 답을 반환

핵심은 **답이 나올 때까지 반복**하는 것입니다. (잘 모르는 부분을 도구로 보완)

> LangChain에서는 `create_agent`로 이 루프를 구현하고, 더 복잡한 경우 **LangGraph**로 그래프를 그려 구현합니다.

### 하이브리드 구조

에이전트의 모든 기능을 LLM으로 구현하는 것은 아닙니다. 실제 시스템은 대부분 하이브리드 구조입니다.

- **LLM**: 판단과 언어 처리
- **일반 코드 / 규칙 / 도구**: 정확성과 재현성이 필요한 작업

LLM은 사용자 요청의 의도를 파악하고 다음 행동을 계획하지만, 실제 수행은 LLM이 아니라 **결정적(deterministic) 실행 계층**이 합니다. 실행 전후에는 검증, 권한, 보안 단계도 거칩니다.

> ⚠️ **주의**: 되돌리기 어려운 작업, 개인정보 및 접근 권한 처리 등은 LLM 판단에만 맡기면 위험합니다. 코드로 조건을 검증하고 **사람의 승인**을 받아야 합니다.

**Workflow vs Agent**
- 정해진 입력을 정해진 순서로 실행 → **Workflow 자동화**
- 어떤 도구를 어떤 순서로 쓸지 그때그때 결정 → **AI 에이전트**에 가까움

👉 **판단이 필요한 부분은 LLM, 확정적으로 실행할 수 있는 부분은 코드와 규칙.**

### 에이전트가 잘하는 일 vs 못하는 일

| ✅ 잘하는 일 | ❌ 못하는 일 |
|---|---|
| 자연어로 된 애매한 요청 해석 | 수치 계산의 정확성이 요구되는 일 |
| 여러 도구를 조합하여 단계적으로 문제 해결 | 최신성이 요구되는 일 (학습 시점 이후 정보는 모름) |
| 언어 중심 산출물 생성 | 100% 재현이 필요한 일 (같은 입력에 다른 출력 가능) |
| 사람이 반복하던 정형화된 리서치·보고 프로세스 자동화 | 파괴적 작업의 무조건 위임 (human-in-the-loop 필요) |

## Part 2. LangChain 기초 개념

### LangChain이란?

레고 블록처럼 필요한 기능을 조립해 LLM 애플리케이션을 빠르게 구축할 수 있게 해주는 **오픈소스 프레임워크**입니다. 부가 기능을 매번 처음부터 구현하는 것은 비효율적이기 때문에 사용합니다.

여러 패키지로 나뉜 생태계이며, 아래에서 위로 쌓이는 계층 구조입니다.

```
1단계 기반   → langchain-core (모든 것의 기초)
      ⇒
2단계 통합   → 각 LLM 제공업체별 통합 패키지
      ⇒
3단계 상위   → langchain (실전용 고수준 기능)
      ⇒
4단계 확장   → langgraph, langserve, langsmith
```

### 메시지 타입

누가 어떤 역할로 말하는지 구분하기 위해 각 메시지에 역할 태그를 붙여, AI가 대화 맥락을 정확히 이해하도록 돕습니다.

| 타입 | 설명 |
|---|---|
| `BaseMessage` | 기본 공통 속성 |
| `SystemMessage` | AI에게 역할과 행동 규칙을 지시 |
| `HumanMessage` | 사용자가 AI에게 보내는 질문·요청 (멀티모달 가능) |
| `AIMessage` | LLM이 생성한 응답 |
| `ToolMessage` | 외부 도구의 실행 결과를 AI에게 전달 |

### 통합 인터페이스

LLM마다 API 형식이 다르므로, 통합 인터페이스로 코드 수정 없이 모델을 바꿀 수 있습니다. 기본 클래스는 `BaseChatModel`입니다.

| 메서드 | 기능 |
|---|---|
| `invoke()` | 한 번 호출하고 완성된 응답을 받음 |
| `stream()` | 응답을 토큰 단위로 실시간 수신 |
| `batch()` | 여러 요청을 병렬 처리 |

> 💡 메서드 앞에 `a` 접두사를 붙이면 **비동기 버전**이 됩니다. (`ainvoke`, `astream`, `abatch`)

### 스트리밍 응답

첫 번째 토큰이 생성되자마자 화면에 표시하는 방식입니다 (`stream()`).
- 사용자 경험(UX) 향상
- 긴 응답 처리에 유리
- 중간 취소 가능

### 모델 파라미터 튜닝

같은 모델이라도 설정값에 따라 응답이 완전히 달라집니다.

- **`temperature`**: 응답의 무작위성(randomness) 제어
  - 낮음 → 확률이 가장 높은 토큰 선택
  - 높음 → 확률이 낮은 토큰도 선택 가능
- **`max_tokens`**: 한 번에 생성할 수 있는 최대 토큰 수 제한
- **`stop`**: 중단 시퀀스. 특정 문자열을 생성하면 즉시 생성을 멈춤

### 비동기 호출과 배치 처리

LLM 호출도 비동기 방식일 때 더 효율적이며, `batch`도 여러 입력을 동시에 처리하므로 효율적입니다.

### 프롬프트 템플릿

편지 양식처럼 **빈칸(변수)이 있는 틀**을 정의해두고, 실행 시점에 빈칸만 채워 완성된 프롬프트를 만듭니다. (매번 수동으로 조합하는 수고 제거)

- `ChatPromptTemplate`: 역할 기반 대화를 템플릿으로 정의
- `MessagesPlaceholder`: 대화 히스토리(이전 대화 내용) 삽입


### Few-shot 프롬프팅

LLM에게 **입력-출력 예시를 몇 개** 보여줘서 원하는 응답 형식과 패턴을 학습시키는 프롬프트 엔지니어링 기법입니다.

- 효과: 패턴 인식, 형식 일관성, 품질 향상
- **동적 예제 선택기 (`ExampleSelector`)**: 입력과 가장 관련성 높은 예시를 자동으로 골라주는 컴포넌트

### 구조화된 출력

| 방식 | 설명 |
|---|---|
| **Output Parser** | 텍스트 응답에서 구조화된 데이터 추출 (text → 구조화 데이터) |
| **`with_structured_output`** | Pydantic 기반으로 모델 레벨에서 출력 형식을 강제 (프롬프트 엔지니어링 ✗, API 레벨 제약 ✓) |

## Part 3. LCEL (LangChain Expression Language)

### LCEL이란?

파이프 연산자 `|`로 Runnable 컴포넌트를 연결하여 **선언적(declarative)** 으로 체인을 구성하는 LangChain의 핵심 프로그래밍 패러다임입니다.

- **선언적** = "어떻게 하는지"(✗)가 아니라 "무엇을 할지"(✓)만 기술
- 모든 컴포넌트가 같은 인터페이스를 가지면, 어떤 것이든 연결할 수 있다.

### Runnable 프로토콜

LCEL의 기반이 되는 표준 인터페이스입니다. LangChain에서 `|`로 연결 가능한 모든 컴포넌트는 이 프로토콜을 구현합니다.

### 파이프 기호 `|`

```python
chain = prompt | model | parser
# 내부적으로 RunnableSequence(first=prompt, middle=[model], last=parser) 생성
```

- OR 연산이 **아니라** 순차 연결입니다.
- 가장 중요한 것은 **입출력 타입의 흐름**입니다. (타입이 잘 호환되어야 함)

### 주요 Runnable 컴포넌트

| 컴포넌트 | 설명 |
|---|---|
| `RunnableSequence` | 여러 Runnable을 순서대로 실행 (`first → middle[0] → … → last`) |
| `RunnableParallel` | 여러 Runnable을 동시에 병렬 실행하고 결과를 딕셔너리로 합쳐 반환. RAG 파이프라인에서 필수적 |
| `RunnablePassthrough` | 입력을 변환 없이 그대로 다음 단계로 전달 |
| `RunnableLambda` | 일반 Python 함수를 Runnable로 변환하는 wrapper. 체인 중간에 간단한 커스텀 로직을 넣을 때 사용 |
| `RunnableBranch` | 조건 함수의 반환값에 따라 어떤 Runnable을 실행할지 동적으로 결정 |

### 체인 디버깅과 시각화

LCEL 체인 구조를 시각화하고, 입출력 스키마를 검사할 수 있습니다.

## Part 4. Tool Calling과 Function Calling

### Tool Calling이란?

LLM이 외부 도구(함수, API)를 호출해야 할 때, **어떤 도구를 어떤 인자로 호출할지 결정**하는 기능입니다. (과거 명칭: Function Calling)

> ⚠️ **LLM은 도구를 직접 실행하지 않습니다.**
> "이 도구를 이 인자로 호출해야 한다"는 구조화된 요청(JSON)을 반환할 뿐이고, 실제 실행은 **우리 코드**가 수행합니다.

> 💡 **3단계 흐름**
> 1. LLM에게 "이런 도구들이 있어"라고 알려줍니다 (**도구 바인딩**).
> 2. LLM이 사용자 질문을 보고 "이 도구를 이 인자로 호출해줘"라고 요청합니다 (**도구 선택**).
> 3. 우리 코드가 실제로 도구를 실행하고, 결과를 LLM에게 돌려줍니다 (**도구 실행**).

### 도구 정의하는 3가지 방법

1. `@tool` 데코레이터
2. `StructuredTool.from_function()`
3. `BaseTool` 서브클래스

### `@tool` 데코레이터

- 일반 Python 함수를 LangChain의 `StructuredTool` 객체로 변환합니다.
- LLM이 필요로 하는 도구·인자 정보를 **자동 추출**합니다.
- **docstring 필수**: 도구의 용도를 알 수 없으면 LLM이 적절한 도구를 선택하지 못합니다.

### Pydantic으로 인자 설명 강화

기본 타입 힌트만으로는 인자에 대한 상세 설명을 LLM에 전달하기 어렵습니다. `BaseModel`과 `Field`를 활용해 각 인자에 **설명, 기본값, 제약 조건**을 추가합니다.

### 바인딩 (Binding)

LLM에게 도구 정보를 알려주는 과정이 **바인딩**이며, `bind_tools()`로 수행합니다.

- 채팅 모델에 도구 목록을 연결하는 메서드
- **새로운 모델 인스턴스를 반환**합니다 (원본은 변경 ✗)

> 💡 **`bind_tools()` 내부 동작**
> 1. 전달받은 도구들의 이름, 설명, 인자 스키마를 JSON Schema로 변환
> 2. 이 스키마를 LLM API 요청의 `tools` 파라미터에 첨부
> 3. LLM이 "도구 호출 필요"라고 판단하면, 응답의 `tool_calls` 필드에 호출 정보를 담아 반환
> 4. LLM이 "도구 호출 불필요"라고 판단하면, 일반 텍스트 응답 반환

- **`tool_choice` 파라미터**: LLM의 도구 선택을 제어 (도구 스키마 구조를 이해하면 디버깅에 도움)
- **`AIMessage.tool_calls`** (리스트 형태): 도구 호출 정보가 담기며, 표준화된 인터페이스라 모델에 관계없이 동일한 방식으로 처리 가능

> 💡 **정리**
> 1. `bind_tools()`는 도구의 JSON 스키마를 모델에 연결
> 2. `tool_choice`로 도구 선택 행동을 제어
> 3. `AIMessage.tool_calls`에서 도구 호출 정보를 표준화된 형태로 받음
> 4. LLM은 한 번에 **여러 도구를 동시 호출** 가능

### ToolMessage와 도구 실행 결과 처리

`bind_tools()`로 모델에 도구를 연결하면, LLM은 `tool_calls`를 반환합니다 (이 시점에 도구는 **아직 실행되지 않음**).

**도구 실행 루프**
```
tool_calls에서 이름·인자 추출
   → 해당 도구 실제 실행
   → 결과를 ToolMessage로 포장
   → 다시 LLM에게 전달
```

- **`ToolMessage`**: 도구 실행 결과를 LLM에 전달하기 위한 전용 메시지 타입. 반드시 `tool_call_id`를 포함해야 하며, LLM이 반환한 `tool_calls`의 `id`와 일치해야 합니다.
- **다중 도구 호출**: 각 결과를 **개별 ToolMessage**로 만들어 모두 메시지 리스트에 추가합니다.
- **에러 핸들링**: 에러 메시지를 ToolMessage의 `content`에 담아 전달하면, LLM이 이를 이해하고 다른 방법을 시도합니다.

> 💡 **정리**
> 1. ToolMessage는 도구 실행 결과를 LLM에게 전달하는 전용 메시지 타입
> 2. `tool_call_id`로 도구 호출 요청과 결과를 매칭
> 3. 실행 루프: `HumanMessage` → `AIMessage(tool_calls)` → `ToolMessage` → `AIMessage(최종 답변)`
> 4. 에러는 ToolMessage의 `content`에 담아 LLM이 처리하도록 위임

### 내장 도구와 커뮤니티 도구

모든 도구를 처음부터 만들 필요는 없습니다. LangChain은 자주 쓰이는 기능을 **내장 도구 / 커뮤니티 도구**로 미리 제공하며, 특히 범용적인 기능은 이미 만들어진 도구를 쓰는 것이 효율적입니다.

실무에서는 여러 도구를 모델에 바인딩하고, LLM이 질문에 따라 적절한 도구를 선택·조합하도록 하여 에이전트를 구성합니다.

> 💡 **정리**
> 1. LangChain은 검색, 위키피디아, 코드 실행 등 다양한 내장/커뮤니티 도구를 제공
> 2. 여러 도구를 함께 바인딩하면 LLM이 질문에 따라 적절한 도구를 자동 선택
> 3. 도구 실행 루프를 범용 함수로 만들면 재사용성이 높아짐
> 4. ⚠️ `PythonREPLTool` 등 코드 실행 도구는 **보안에 각별히 주의**
