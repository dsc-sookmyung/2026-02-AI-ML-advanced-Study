# Ch.08 RAG(검색 증강 생성) 파이프라인

## RAG(Retirival-Augmented Generation)

**LLM의 환각을 잡는 핵심 패턴**

- LLM이 답변을 생성하기 전에 외부에서 관련 정보를 검색, 정보를 컨텍스트로 함께 제공해 답변의 정확도를 높이는 패턴
- 모델 자체를 수정하지 않고 프롬프트에 검색된 문서를 추가
- 빠르고 경제적인 방식

**RAG 파이프라인**

1단계. 인덱싱: 문서를 청크로 나누고, 임베딩하여 벡터 DB에 저장

2단계. 검색: 사용자 질문과 유사한 문서 청크를 벡터 DB에서 검색

3단계. 생성: 검색된 문서, 질문을 LLM에 전달해 답변 생성

환각(Hallucination): AI가 마치 아는 것처럼 그럴듯한 숫자를 만들어내는 것

그라운딩(Grounding): LLM의 답변을 실제 데이터나 문서에 근거하여 생성

### RAG 프롬프트 엔지니어링

답변의 품질을 향상시키기 위해 명확한 지시가 포함된 프롬프트가 필요

**프롬프트 패턴**

1. 역할 부여: 명확한 역할 부여
2. 컨텍스트 주입: 검색된 문서 삽입 위치 지정
3. 답변 제약: 문서에 없는 내용 답변 금지
4. 출처 인용: 답변 근거 명시
5. 형식 지정: 답변 형식 통일

같은 검색 결과라도 프롬프트에 따라 답변 품질이 달라짐

모르면 모른다고 답변하게 만드는 것이 중요

### create_stuff_documents_chain과 create_retireval_chain

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| LCEL 직접 구성 | 유연한 커스터마이즈, 구조 이해 | 코드가 다소 길어짐 |
| 헬퍼 함수 | 간결한 코드, 빠른 프로토타이핑 | 내부 동작 파악 어려움 |

### 고급 Retriever

검색시 단순 질문에만 의존하지 않고 관련 문서를 결합해 검색 품질을 높이는 기법

**MultiQueryRetriever(멀티쿼리 리트리버)**

사용자의 원본 질문을 LLM으로 여러 변형 질문으로 재작성하고 결과를 합쳐 더 다양한 문서를 찾는 기법

**동작 과정**

1. 원본 질문 입력
2. LLM이 3~5개의 변형 질문으로 변환
3. 각 변형 질문으로 벡터 스토어 검색
4. 결과 합산, 중복 제거
5. 최종 문서 리스트 반환

변형 쿼리 생성시 쿼리당 추가 LLM 호출이 1회 발생

**ContextualCompressionRetriever(문맥 압축 리트리버)**

검색된 문서에서 질문과 관련 있는 부분만 추출해 LLM,에 전달, 불필요한 부분 제거

컨텍스트 품질을 높이고 토큰 비용 절약 가능

- EmbeddingsFilter: 임베딩 유사도를 기준으로 문서를 필터링
    - LLM 호출 X
    - 문서 내용 변형하지 않고 문서 전체를 제거
- LLMChainExtractor: 각 문서에서 질문과 관련된 부분만 추출
    - LLM 호출 → 비용 발생

비용과 정확도의 트레이드오프를 고려해 선택

**EnsembleRetriever**

벡터 검색과 키워드 검색을 가중결합

의미 + 키워드 검색의 장점 결합

### 대화형 RAG: 히스토리 인식 검색

대화의 연속성을 위해 챗봇에서 히스토리를 인식하며 각 질문의 맥락을 이해

**create_history_aware_retriever의 동작 원리**

대화 히스토리 + 현재 질문 → 검색 쿼리 재작성 함수

대명사나 문맥 의존 커리를 독립적인 검색 쿼리로 변환

**동작 과정**

1. 대화 히스토리가 없는 경우: 사용자 질문을 그대로 검색기에 전달
2. 대화 히스토리가 있는 경우: LLM에서 히스토리 + 현재 질문을 분석해 독립적인 검색 쿼리 생성
3. 재작성된 쿼리로 벡터 스토어 검색

ex)

> 
> 
> 
> "LangChain이 뭐야?" → AI 답변
> 
> "그걸로 RAG를 어떻게 만들어?"
> 

“그것”=”LangChain”

create_history_aware_retriever이 “그것”을 “LangChain”으로 재작성해 검색

create_history_aware_retriever + create_retrieval_chain 조합으로 사용

### RAG 평가와 품질 개선 전략

RAG 파이프라인을 객관적으로 측정하고 개선

**검색 품질 vs 생성 품질**

검색(Retrieval) 품질

- 컨텍스트 관련성: 검색기가 질문과 관련 있는 문서를 잘 찾았는가
- 컨텍스트 재현율: 정보가 검색 결과에 모두 포함되었는가

생성(Generation) 품질

- 충실도: 검색된 문서에 없는 내용을 지어내지 않았는지 확인
- 답변 관련성: 답변이 질문에 적절히 대답하는가

**RAG 품질 개선 전략**

| 문제 | 원인 | 개선 전략 |
| --- | --- | --- |
| 엉뚱한 문서 검색 | 검색 품질 낮음 | chunk_size/overlap 조정, 임베딩 모델 변경, MMR 사용 |
| 필요한 정보 누락 | 검색 범위 부족 | k값 증가, MultiQueryRetriever 적용 |
| 환각 발생 | 생성 충실도 낮음 | 프롬프트 강화, temperature 낮추기 |
| 답변이 장황함 | 불필요한 컨텍스트 | ContextualCompression 적용, chunk_size 줄이기 |
| 응답 속도 느림 | 검색/생성 병목 | 캐싱, 임베딩 모델 경량화, 스트리밍 적용 |
- 키워드 기반 평가는 데모용, 실무에서는 LLM 기반 판단 사용

### 리랭킹(Reranking)

리랭킹 모델이 질문과 각 문서의 관련성을 더 정밀하게 판단해 순서를 재정렬

1차 검색 - 벡터 유사도: 빠름, 대략적 관련성

2차 리랭킹 - Cross-Encoder 모델 : 느리지만 정확, 상위 K개 처리

### 청크 크기(chunk_size) 최적화

chunk_size는 RAG 품질에 가장 큰 영향을 미치는 파라미터

- 너무 작으면 문맥이 끊기고, 너무 크면 관련 없는 내용이 섞임
- chunk_overlap: chunk_size의 10~20%로 설정

| chunk_size | 장점 | 단점 |
| --- | --- | --- |
| 작은 값(200 ~ 500)  | 정확한 검색, 적은 노이즈 | 맥락 부족, 문장 단위 분리 |
| 중간 값(500 ~ 1000) | 균형 잡힌 검색 | - |
| 큰 값 (1000 ~ 2000) | 풍부한 맥락 | 노이즈 포함, 토큰 비용 증가 |
