# Ch 13: 멀티 에이전트 시스템: Supervisor와 Swarm

### 멀티 에이전트 아키텍처 (Multi-Agent Architecture)

여러 개의 전문화된 AI 에이전트가 서로 협력하여 복잡한 작업을 수행하는 시스템 구조

각 에이전트는 고유한 역할, 도구, 프롬프트 가지며 정해진 규칙에 따라 작업을 주고 받음

대표적인 멀티 에이전트 패턴

| 기준 | Supervisior | Swarm | Hierarchical |
| --- | --- | --- | --- |
| 작업 흐름 | 중앙에서 순서 결정 | 에이전트가 자율적으로 결정 | 팀 단위 분리 |
| 적합한 상황 | 작업 순서가 중요할 때 | 에이전트 간 직접 대화가 필요할 때 | 팀 여러개, 규모가 클 때 |
| 복잡도 | 낮음 | 중간 | 높음 |
| LLM 호출 수 | 중간 | 적음 | 많음 |

## Supervisor 패턴: 중앙 지휘자가 에이전트를 조율

사용자의 요청을 분석하고, 적절한 전문 에이전트에게 작업을 위임해 최종 결과를 취합

1. 사용자 요청 받기
2. 적절한 에이전트 선택 (내부적으로 핸드오프 도구 호출)
3. 선택된 에이전트가 작업 수행
4. 결과가 Supervisor에게 돌아옴
5. 작업 완료시 최종 답변 생성

Tool Calling 메커니즘을 활용한 에이전트 전환

**Supervisor 기본 구성**

researcher(조사) 에이전트와 writer(작성) 에이전트를 만들고 Supervisor가 조율

**Supervisor에 커스텀 프롬프트 적용**

Supervisor의 행동을 더 세밀하게 제어

1. 작업 순서
2. 각 에이전트 역할 설명
3. 품질 기준
4. 에러 처리 지침

커스텀 프롬프트로 순서, 규칙, 출력 형식 등을 명시

** 에이전트의 name 파라미터를 빠뜨리면 Supervisor가 에이전트 구분 불가능 **

**Supervisor 패턴의 내부 동작 정리**

1. 사용자 요청 수신 : messages에 HumanMessage 추가
2. Supervisor LLM 호출: 프롬프트 + 핸드오프 도구 목록 전달
3. 에이전트 선택: tool_calls에 transfer_to_{name} 반환
4. 에이전트 실행: 선택된 에이전트 노드로 제어권 이동
5. 결과 반환: 에이전트의 AIMessage가 messages에 추가
6. Supervisor 재호출: 다음 에이전트 선택 or 최종 답변 생성

## Swarm 패턴: 에이전트 간 자율 핸드오프

중앙 지휘자 없이 에이전트들이 핸드오프 도구를 사용해 자율적으로 다음 에이전트에게 작업을 넘기는 **탈중앙화 협업 패턴**

**Swarm 패턴의 동작 원리**

1. 각 에이전트가 핸드오프 도구를 등록
2. 에이전트가 스스로 판단
3. 제어권이 직접 이동
4. 대화 맥락이 유지

직접 핸드오프를 통해 Supervisor 오버헤드 없이 빠르게 전환

전환이 빈번한 시나리오에 최적 (ex. 고객 지원, 상담 시스템)

**핸드오프 도구 커스터마이징**

기본 핸드오프만으로 문맥 전달이 어려울 수 있음

name, description 세밀하게 설정 → LLM이 핸드오프 시점과 방법 더 정확히 판단

** 핸드오프 경로를 순환 없이 설계하거나, 체크포인터 없이 멀티 턴 대화를 시도하지 않도록 주의 **

**Swarm에서 active_agent 추적**

active_agent : 어떤 에이전트가 대화를 담당하는지

- 대화 시작: active_agent = default_active_agent
- 핸드오프 발생: active_agent = “target_agent_name”
- 다음 호출: 체크 포인터에 저장된 active_agent의 에이전트가 바로 시작

→ 마지막으로 활성화된 에이전트가 자동으로 이어 받음

→ Swarm에서 체크포인터 필수

## 계층적 멀티 에이전트: Supervisor of Supervisors

### 계층적 패턴(Hierarchical Pattern)

여러 개의 Superviosr팀을 상위 Superviosr가 조율하는 다단계 구조

각 팀은 독립된 서브그래프로 구성, 상위 Supervisor가 팀 단위로 작업을 위임

**핵심 장점**

- 관심사 분리: 전문 영역에만 집중
- 확장성: 새 팀 추가해도 다른 팀에 영향 X
- 독립적 테스트: 서브 그래프 단독 테스트 가능

실사용 예시: 리서치팀, 개발팀, QA팀을 별도 서브그래프, 상위 PM 에이전트가 조율

**계층적 패턴 연결**

create_supervisor()로 팀 생성 → Supervisor 에이전트 리스트에 전달 → 서브그래프 등록

- 내부 상태(메시지, 호출 도구 등)는 팀 안에서만 유지
- Supervisor에거 팀의 최종 결과만 전달

**계층 구조 설계 시 고려사항**

| 고려사항 | 권장 사항 | 이유 |
| --- | --- | --- |
| 팀당 에이전트 수 | 2~4개 | Superviosr의 선택 정확도 유지 |
| 계층 깊이 | 2~3단계 | 깊이 깊으면 레이턴시 증가 |
| 팀 간 의존성 | 최소화 | 독립적 테스트, 유지보수 용이 |
| output_mode | 하위팀-”last_message”, 최상위: “full_history” | 중간 과정 노이즈 제거 |

### 에이전트 간 상태 공유와 통신

리서치 에이전트가 수집한 자료를 작성 에이전트가 참조, 작성 에이전트의 결과를 검수 에이전트가 받음

**메시지 패싱(Message Passing) 방식**

에이전트들이 공유 상태의 메시지 리스트에 메시지 추가 → 다른 에이전트가 메시지 읽어서 맥락 파악

(ex. 게시판)

** create_supervisor()과 create_swarm이 내부적으로 MessageState를 공유 상태로 사용

- 에이전트 간 상태가 어떻게 공유되는지 이해
- LangSmith 트레이싱으로 시각적으로 확인

### full_history vs last_message

“full_history”: 모든 에이전트의 전체 대화 내역이 유지

- 맥락 공유가 중요한 경우
- 정확한 판단 가능
- 토큰 수가 많아져 비용 증가
- 팀 내부 사용

“last_message”: 각 에이전트의 마지막 메시지만 유지

- 결과만 필요한 경우
- 이전 에이전트 작업을 다음 에이전트가 알 수 없음
- 토큰 절약
- 팀 간 사용
