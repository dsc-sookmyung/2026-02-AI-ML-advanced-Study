## 📝 프로젝트 개요

### 프로젝트명

**CareerFit — RAG 기반 맞춤형 자기소개서 작성 Multi-Agent**

### 한 줄 소개

Obsidian에 기록한 개인 경험을 하이브리드 검색(BM25 + Embedding)으로 추천하고, 사용자가 선택한 경험만을 근거로 Writer–Reviewer Agent가 자기소개서를 작성·검증하는 시스템

### 기획 배경 및 문제 정의

자기소개서를 작성할 때마다 여러 프로젝트·대외활동 기록을 다시 살펴보고, 채용 공고 및 문항에 맞는 경험을 선택하는 데 시간이 든다. LLM으로 곧바로 초안을 생성하면 본인이 실제로 수행하지 않은 역할이나 성과가 포함될 위험(Hallucination)도 있다.

이를 개선하기 위해 **개인 경험을 구조화하여 관리하고, 검색 근거를 확인한 뒤 사용자가 활용 경험을 직접 선택하는 과정**을 도입한다. 이후 작성과 검토를 분리한 Multi-Agent 구조를 적용하되, 검토는 막연한 LLM 평가가 아니라 **주장(claim) 단위 근거 매칭**과 **결정적 규칙 검사(글자 수)**로 구조화한다. NLP 스터디에서 학습한 Embedding, RAG, Tool Calling, LangGraph, Human-in-the-loop를 실제 개인 문제에 적용하는 것이 목적이다.

## 🎯 목표

- **핵심 목표**: 개인 경험에 근거한 자기소개서 초안을 작성하고, ① 검색 방식, ② RAG 유무, ③ Reviewer 유무에 따른 효과를 베이스라인과 비교하여 검증한다.

### 우선순위

| 구분           | 범위                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Must (MVP)** | 경험 노트 20개 이상 구축, 하이브리드 검색 + Hit@3/MRR 평가(랜덤 베이스라인 포함), 경험 선택 HITL(일시 중단·재개), Writer + 주장 단위 Reviewer, 글자 수 검사 Tool, 베이스라인 ①·② 비교 |
| **Should**     | 베이스라인 ③(Writer 단독 vs Writer + Reviewer), LangSmith 실행 추적, 실패 사례 분석                                                                                                   |
| **Could**      | 경험 선택 화면 웹 UI, 증분 인덱싱, 자소서 버전 관리, 면접 예상 질문 생성                                                                                                              |
| **Later**      | 일정·학습 Agent와 Supervisor로 통합하는 Personal AI OS 확장                                                                                                                           |

### 최소 구현 범위 (MVP) 상세

1. Obsidian에 **프로젝트 개요 노트**와 **개별 문제 해결 경험 노트**를 분리해 기록하고 내부 링크로 연결한다. 경험 노트는 **20개 이상**을 목표로 한다.
2. Python으로 Markdown 및 YAML Properties를 읽고, Kiwi 형태소 분석 기반 **BM25 인덱스**와 **Embedding 인덱스(Chroma)**를 함께 구축한다.
3. 채용 공고 텍스트, 자기소개서 문항, 글자 수 제한(공백 포함/제외 기준 명시)을 입력받아 요구 역량을 분석한다.
4. 두 검색 결과를 **RRF(Reciprocal Rank Fusion)**로 결합하여 관련 경험 **Top 3**와 추천 이유·근거 노트 ID를 보여준다.
5. **사용자가 사용할 경험을 선택하기 전에는 작성 단계로 진행하지 않는다.** (LangGraph `interrupt` + Checkpointer)
6. Writer Agent는 **선택된 경험 노트와 연결된 프로젝트 개요만** 맥락으로 받아 초안을 작성한다.
7. Reviewer Agent는 다음 순서로 검토한다.
   - (a) 초안에서 핵심 주장 추출 → 각 주장에 근거 노트 ID 매칭 → **근거 없음 / 원문과 충돌** 주장 표시
   - (b) 문항 적합성·구체성 루브릭 점수 산출
   - (c) 글자 수는 LLM이 아닌 **Python Tool**로 검사
8. 최초 작성 후 **최대 2회 재작성**하며, 마지막 버전이 아니라 **검토 점수가 가장 높은 버전**을 최종본으로 채택한다. 미해결 문제를 표시한 초안을 CLI로 출력한다.

## 👉 태스크 & 접근 방법

- **태스크 유형**: 의미 기반 검색 / 하이브리드 검색 / RAG / 조건부 텍스트 생성 / 근거 검증 / Multi-Agent 워크플로
- **사용할 모델 (후보)**:
  - **생성 LLM**: API 기반 모델 우선 사용. 한국어 성능·비용을 1주차에 소규모로 비교 후 선정
  - **Embedding**: `intfloat/multilingual-e5-small` (문서는 `passage: `, 질의는 `query: ` 접두어 적용). 필요시 `-base` 또는 `BAAI/bge-m3`와 비교
  - **키워드 검색**: `kiwipiepy` 형태소 분석 + `rank_bm25`
- **접근 방법**:
  - 별도 파인튜닝 없이 **프롬프트 엔지니어링 + RAG**로 시작한다.
  - 각 경험 노트를 검색 단위로 인덱싱하고, 메타데이터(문서 유형, 프로젝트 ID, 역량 태그, 기간)를 함께 저장한다. 선택된 경험에 연결된 프로젝트 개요와 원문은 노트 ID로 조회한다.
  - LangGraph 흐름:
    **공고·문항 분석 → 하이브리드 검색 → 사용자 선택(interrupt/resume) → Writer → Reviewer(주장 추출·근거 매칭·루브릭) → 글자 수 Tool → 조건부 재작성(최대 2회) → 최고 점수 버전 출력**
  - 글자 수 대응: Writer는 한도의 **약 90%**를 목표로 작성하고, 초과 시 Python 검사 결과(초과 글자 수)를 피드백으로 전달하여 축약한다.
  - 결정적인 작업(글자 수, 노트 ID 조회, 점수 비교)은 Python 함수로, 서술·평가는 LLM 노드로 수행한다.
- **선택 이유**: 소규모 한국어 코퍼스에서는 고유명사·기술명 매칭(BM25)과 의미 유사도(Embedding)가 상호 보완적이다. Human-in-the-loop로 경험 선택권을 보장하고, Reviewer를 주장 단위로 구조화하여 같은 LLM의 자기 평가 편향을 줄인다.

## 📏 평가 방법

- **평가 지표**:
  - **경험 검색**: 질의별 정답 목록 기준 **Hit@3, MRR**. 코퍼스가 작으므로 **랜덤 추천의 기대 Hit@3를 함께 보고**하여 실제 개선폭을 해석
  - **근거 일치**: 생성문의 핵심 주장 중 근거 노트가 매칭된 비율(**Grounded Claim Rate**), 원문과 충돌하는 주장 수. Reviewer 자동 판정과 수동 판정의 일치율도 확인
  - **조건 준수**: 문항 요구사항 충족 여부, 글자 수 제한 준수율(공백 포함/제외 기준 명시)
  - **자소서 품질**: 문항 적합성·구체성·자연스러움 루브릭(1~5점). 조건을 가리고 순서를 섞은 **블라인드 평가**로 진행하며, 가능하면 지인 1~2명의 평가 추가
  - **효율**: 평균 실행 시간, LLM 호출 횟수, 토큰 사용량 및 추정 API 비용
- **베이스라인**:
  1. **검색 비교**: 랜덤 vs BM25 단독 vs Embedding 단독 vs **하이브리드(RRF)**
  2. **RAG 효과**: 동일 문항·공고에 대해 **RAG 없이 LLM 초안 작성** vs **선택 경험을 제공한 초안 작성**
  3. **Multi-Agent 효과**: 동일한 검색 결과·문항으로 **Writer 단독** vs **Writer + Reviewer 및 수정 루프(최고 점수 버전 채택)**
  - 비교 조건(모델, temperature, 프롬프트 외 변수)을 고정하고, 결과는 **소규모 실험의 탐색적 결과**로 해석한다. 근거 검증은 원본 노트와의 일치 여부를 판단하는 것이며 실제 경력의 진실성을 자동으로 보증하지는 않는다.

## 🛠️ 기술 스택

- **언어 / 프레임워크**: Python, LangGraph(+ Checkpointer), Sentence Transformers, Chroma, kiwipiepy, rank_bm25, Obsidian(Markdown/YAML)
- **생성 LLM**: API 기반 모델(1주차 선정), 환경 변수로 API 키 관리. 선택된 노트만 API로 전송하여 외부 전송 개인 정보 최소화
- **실험 환경**: 로컬 CLI 실행, 실험 결과는 CSV/JSON으로 기록, LangSmith로 실행 흐름·LLM 호출 추적(선택)
- **(Could) 서빙 / 데모**: 경험 Top 3 확인·선택 화면을 웹 UI로 구현(React 또는 Streamlit), 이후 필요시 API 서버로 확장
